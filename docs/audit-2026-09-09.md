# Stabilization audit — 2026-09-09

Base: `5b91cbb789005caac017e95de903153417150635` (main).

Engine: actual `opencode2 v0.0.0-beta-18743`.

## Основной вывод

Главная проблема — не количество моделей, а несовпадение контрактов между
реальным V2 runtime, плагинами, TUI и тестовыми моками. Успешный unit-test
плагина не доказывал его загрузку на чистой машине. Браузерные проверки и
статические assertions местами требовали противоположного поведения.

Этот пакет исправляет воспроизведённые дефекты и добавляет повторяемую приёмку.
Он не означает доказательство отсутствия всех дефектов, проверку каждого API
провайдера или завершение всех возможных функций «идеального агента».

## Воспроизводимая приёмка

```bash
# Model-free matrix: сохраняет каждый лог и JSON, не обрывает отчёт на первом FAIL.
python3 scripts/audit-regression.py --output /tmp/opencode-audit

# Полностью отдельный HOME, настоящий install.sh и настоящий native backend/TUI.
# CLI и pinned Ponytail скачиваются штатно. Никаких реальных provider keys не нужно.
python3 scripts/install-native-regression.py --output /tmp/opencode-native
```

Для сети без доступа к npm/GitHub второй harness принимает `--cli-prefix` с
ранее скачанным настоящим npm prefix и `--ponytail-url` с настоящим upstream
Git bundle. Это preseed зависимостей, не подмена CLI или SDK моками. Именно этот
вариант использовался в локальном изолированном контейнере.

`clean-regression.yml` теперь имеет отдельные gates `model-free-matrix` и
`native-clean-install`. Логи сохраняются также при ошибке. Транспортный
workflow первоначального аудита не является доказательством регресса.

### Что проверяет matrix

20 отдельных наборов: core verification; Runtime V3; routing/effort; install/update
fixtures; bootstrap; pinned Ponytail provisioning; composed HTTP server;
web security; runtime invariants; queue reconciliation; TUI panel/dialog logic;
TUI clipboard; slash submission; stream rendering; browser queue badges;
full desktop/mobile browser fixtures; production frontend with fixture backend;
critical browser controls; packaged real TUI at 80x24/120x30/160x40; integration contract.

Новый backend isolation набор из 15 тестов воспроизвёл 12 отказов на исходном
коде, затем прошёл после исправлений. Новый host/state boundary набор содержит
проверки вредоносных значений host и конкурентной записи. Native receipt bug
дополнительно воспроизведён на реальном движке, а не только на моках.

### Что проверяет реальная установка

Штатный `install.sh`, pre-install gates, реальные plugin/catalog/session APIs,
обычный web login, оба post-install self-test, нативные model/provider/MCP/profile/
skill/orchestration CRUD, rollback на inline secret, reload и режимы Ponytail.

Native TUI smoke открывает и отменяет provider/model/MCP/profile/skill/orchestration
визарды, `/configure`, `/server`, `/webserver`, model picker и шесть panel views.
Он не заменяет все возможные ручные keyboard/mouse сценарии; диалоговые ветвления
и CRUD отдельно проверяются fixtures и реальным backend. Счётчики real session
проверяются на нулевые model tokens/cost. Служебные тестовые элементы удаляются.

## Границы результата

* Реальные платные model completions, provider tool-calling и лимиты подписок не
  вызывались. Наличие модели в каталоге не является live-проверкой её API.
* RAG/Qdrant corpus и DipTrace на пользовательском компьютере не проверялись:
  в clean room они намеренно отключены. Их отсутствие не превращается в PASS
  интеграции; проверена работоспособность основного продукта без этих компонентов.
* В локальном контейнере нет user-systemd. Проверен настоящий foreground/manual
  install; systemd deployment проверен fixtures, но не реальным user manager.
* Настоящий bubblewrap доступен, но kernel запрещает создание namespaces (`EPERM`).
  Проверены policy/containment/fail-closed tests; успешная kernel sandbox execution
  локально не заявляется и защита ради зелёного статуса не отключалась.
* Реальный терминал VS Code/WSL, clipboard хоста, Wayland/X11, Android/iOS PWA,
  внешняя сеть/Tailscale/TLS proxy не воспроизводились этим Linux PTY/Chromium.
* Multi-user login не следует считать полноценной multi-tenant изоляцией проектов,
  task stores и credentials. Внешняя публикация требует отдельной threat-model
  и контроля сетевого доступа. Это не сертификация полной безопасности.

## Дальнейшая архитектура

Следующее расширение должно идти от общих контрактов: один durable owner сессии,
коррелированные результаты команд, один model registry, явные client capabilities,
один permission/ownership gateway. Не следует добавлять ещё один независимый
оркестратор или ещё один слой monkey-patching интерфейса. Изменения движка должны
проходить native install и PTY gates до изменения pin. Новые provider profiles
должны иметь отдельную opt-in live acceptance, а не проходить лишь по имени модели.
